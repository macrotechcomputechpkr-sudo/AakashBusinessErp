# Deep-Scan Findings & Fixes

## Critical bugs (would crash or silently corrupt data)
1. **`companyRoutes.js` / `fiscalYearRoutes.js` used `jwt.verify()` without importing `jsonwebtoken`.**
   Every protected call crashed with `ReferenceError: jwt is not defined` -> HTTP 500.
   Fixed by introducing `server/middleware/auth.js` (`requireAuth`) used everywhere.

2. **Two incompatible backend stacks (Node/Express + Python/Flask) cannot run as one server.**
   The "User Management" module was written in Flask while everything else was Express.
   Consolidated: user/department/designation/security-group routes rewritten in Express
   (`server/routes/userRoutes.js`, `departmentRoutes.js`, `designationRoutes.js`,
   `securityGroupRoutes.js`).

3. **Supabase `service_role` key (and even the `anon` key) were sent to the browser and
   stored in `localStorage`**, and the frontend created a Supabase client directly in
   the browser. This is a critical security hole - anyone can read it from devtools.
   Fixed: the backend never returns `master_db_*` fields to the client; the frontend now
   only talks to our own API (`authFetch` in `AuthContext.jsx`), which is the only thing
   holding DB credentials.

4. **Login could crash (`.single()` on multiple rows) if the same email existed under
   two different tenants.** Fixed: login now requires `tenant_code` to disambiguate when
   more than one match exists, instead of throwing.

5. **`employee_code` / `department_code` / `designation_code` were generated by reading
   the "last" row and adding 1 in application code** - classic race condition, two
   concurrent "create user" requests can get the same code. Fixed with Postgres
   sequences + `next_employee_code()` / `next_department_code()` / `next_designation_code()`
   functions (`database/03_functions_triggers.sql`), called via Supabase RPC.

6. **No unique constraint on `employee_code`** even though the app assumed it was unique.
   Added `unique_tenant_employee_code`.

7. **Fiscal years had no overlap protection.** Added a Postgres `EXCLUDE` constraint
   (`btree_gist`) so two fiscal years for the same tenant can never overlap; the API
   translates the resulting DB error into a friendly 400 message.

## Frontend bugs
8. **`AuthContext.jsx`: `requiresCompanyCreation: user?.tenant?.is_company_created`** -
   the login API returns `tenant` as a sibling of `user`, never nested inside it, so this
   was always `undefined`/falsy and the "finish company setup" redirect never fired.
   Fixed to read the API's explicit `requires_company_creation` field.

9. **`Dashboard.jsx` called `GET /api/tenant/:id/dashboard`, which did not exist on the
   backend** (always 404, silently swallowed). Added `server/routes/dashboardRoutes.js`.

10. **The whole "User Management" page was a static HTML/JS demo with an in-memory
    `users` array** - it never called any backend, so "CRUD complete" was not true;
    data vanished on refresh. Replaced with `client/src/pages/UserManagement.jsx`,
    which is wired to the real API.

## "Listing / column setting not working" (your report)
11. There was **no search, sort, or pagination** on the users list - `/api/users/list`
    always returned every row. Fixed in `userRoutes.js` (`applyListQuery` helper) with
    `?search=&sortBy=&sortDir=&page=&pageSize=`.
12. There was **no column show/hide ("column settings") anywhere** in the old table.
    Added `client/src/components/DataTable.jsx` - a reusable table with a "⚙️ Columns"
    menu (persisted per-browser via localStorage), sortable headers, search box, and
    Previous/Next pagination.

## Enter-key focus
13. The old inline script could **trigger form submission twice** for the last field
    (once via `next.click()` on the submit button, again via a dispatched submit event),
    and used the `[disabled]` CSS attribute selector as its only visibility check, which
    can lag a tick behind a just-toggled `display:none` section.
    Replaced with `client/src/hooks/useEnterKeyNavigation.js`: a single reusable hook
    that uses `offsetParent !== null` for reliable visibility, and calls
    `form.requestSubmit()` exactly once from the last real field.

## Advanced-but-optional fields added to master tables (as requested, no new modules)
- **departments**: `parent_department_id` (department hierarchy), `cost_center_code`,
  `display_order`.
- **designations**: `default_department_id`, `grade` (salary/grade band), `display_order`.
These are nullable/optional so existing rows and forms keep working unchanged.

## Known limitation flagged, not silently left in
- The hand-rolled Nepali (Bikram Sambat) date converter uses an approximate leap-year
  rule; real BS month lengths come from an official irregular table and can drift for
  some years. The obvious off-by-one bug in month resolution is fixed, but for anything
  legally/financially significant (tax filings, printed invoices), swap in a maintained
  BS↔AD data table/library. This is called out in a comment at the top of
  `nepaliDateUtils.js`.

## How to apply
1. Run `database/01_global_master_schema.sql`, then `02_tenant_master_schema.sql`,
   then `03_functions_triggers.sql` (in that order) against a fresh database.
2. Generate a real bcrypt hash for the super-admin password and insert it manually
   (see the commented-out `INSERT` at the bottom of `01_global_master_schema.sql`) -
   do not commit real password hashes to source control.
3. `cd server && cp .env.example .env` and fill in real values, then `npm install && npm run dev`.
4. Point the React app's `REACT_APP_API_URL` env var at the backend, then drop in the
   fixed files under `client/src/...` (they are additive/replacing, not a whole new app).
